Project Overview
Dynamic Docs is a Next.js application for role-based document generation.
Users authenticate with Firebase phone OTP. After OTP verification, the backend
decides whether the mobile number belongs to an Admin, an existing Customer, or
a new Customer.

Admins assign document names to customer mobile numbers. Customers view the
documents assigned to their mobile number, select a document type, fill a form,
and generate a PDF for download or preview.


Technology Stack
- Framework: Next.js 15 using Pages Router
- Language: TypeScript and React
- UI: Material UI, Emotion, global CSS
- Forms: Formik
- Validation: Yup
- Authentication: Firebase phone OTP with invisible reCAPTCHA
- PDF generation: @react-pdf/renderer
- HTTP client: Axios
- Notifications: react-toastify
- Testing: Jest, next/jest, jsdom, React Testing Library

Firebase OTP Authentication Flow
Main file: src/PageComponents/components/LoginForm.tsx

Flow:
1. User opens /loginPage.
2. LoginComponent mounts.
3. The component creates an invisible Firebase RecaptchaVerifier.
4. User enters a 10-digit mobile number.
5. When the mobile number reaches 10 digits, sendOTP() runs.
6. sendOTP() calls:
   signInWithPhoneNumber(firebaseAuth, "+91" + mobile, appVerifier)
7. Firebase sends OTP to the mobile number.
8. The Firebase ConfirmationResult is stored on window.confirmationResult.
9. User enters a 6-digit OTP.
10. LoginComponent calls:
    window.confirmationResult.confirm(otp)
11. If OTP confirmation succeeds, mobileVerified becomes true.
12. The Login button becomes enabled.
13. User submits the login form.

Error cases:
- If reCAPTCHA is not initialized, the app shows:
  "Recaptcha is not initialized."
- If OTP send fails, the app shows:
  "Failed to send OTP: <error message>"
- If OTP confirmation fails, the app shows:
  "Invalid OTP!"


Role-Based Login Flow
After OTP verification, LoginComponent calls:
loginApi({ mobile })

The backend response controls navigation.

Admin:
- If response.userType is "Admin":
  User is routed to:
  /addDocuments?adminMobile=<mobile>&userType=Admin

Existing Customer:
- If response.userType is "Customer" and response.isExistingUser is true:
  User is routed to:
  /docListPage?mobile=<mobile>&userType=Customer

New Customer:
- If response.isExistingUser is false:
  User is routed to:
  /registerForm?mobile=<mobile>

Important note:
The frontend routes users based on role, but backend APIs should still enforce
authorization. The frontend should not be treated as the only security layer.


Auth Token Handling
File: src/axios.tsx

Token storage:
- Firebase ID token is stored in localStorage under:
  auth-token

setAuthToken(token):
- Stores the token in localStorage.

Axios interceptor:
- Reads auth-token from localStorage.
- Adds Authorization header:
  Bearer <token>
- Adds X-Brand header:
  DD

Sign out:
- Header and PublicHeader call Firebase signOut().
- After sign out, auth-token is cleared.
- User is routed back to /.

Important implementation note:
src/apiData/api.tsx currently imports axios directly from the axios package.
Because of that, the configured Axios instance from src/axios.tsx may not be
used by those API calls. If auth headers are required for all backend calls,
api.tsx should import the configured instance from src/axios.tsx.


Admin Document Assignment Flow
Main file: src/pages/addDocuments/index.tsx

Purpose:
Admin assigns document names to a customer mobile number.

Query parameter:
- adminMobile
  Read from the URL using useParams().

Flow:
1. Admin logs in through Firebase OTP.
2. Backend returns userType "Admin".
3. App routes Admin to /addDocuments.
4. Admin enters a customer mobile number.
5. When the customer mobile number reaches 10 digits, the app calls:
   getDocumentsNameApi(mobile)
6. Existing documents assigned to that customer are displayed.
7. Admin can add document input fields by clicking Add Document.
8. Admin enters one or more document names.
9. Admin submits the form.
10. The app sends this payload to addDocumentsApi():
    {
      adminMobile,
      mobile,
      documents
    }
11. If the backend returns status 200:
    - existingDocsList is updated with response.documents
    - success toast is shown

Removing documents:
1. Admin clicks delete on an existing document.
2. The app calls:
   removeDocumentApi(mobile, docName, adminMobile)
3. Backend removes the assigned document.
4. UI updates existingDocsList from response.documents.

Validation:
- Customer mobile number is required.
- Mobile number must be exactly 10 digits.


Customer Document List Flow
Main file: src/pages/docListPage/index.tsx

Purpose:
Customer views assigned documents and selects one to generate.

Query parameter:
- mobile
  Customer mobile number.

Flow:
1. Customer logs in through Firebase OTP.
2. Backend confirms existing Customer.
3. App routes Customer to /docListPage.
4. docListPage reads mobile from URL query parameters.
5. App calls:
   getDocumentsNameApi(mobile)
6. Backend returns assigned document names.
7. Documents are displayed as radio options.
8. Customer selects a document type.
9. On submit, whitespace is removed from selected document name.
10. App routes to:
    /inputFormPage?mobile=<mobile>&documentType=<documentType>

Example:
If selected document name is "Sample Offer Letter", it becomes:
SampleOfferLetter


New Customer Registration Flow
Main file: src/pages/registerForm/index.tsx

Purpose:
Register new customers after OTP verification.

Query parameter:
- mobile
  Mobile number from login flow.

Flow:
1. New user completes Firebase OTP verification.
2. Login API says user does not exist.
3. App routes to /registerForm?mobile=<mobile>.
4. User enters full name.
5. App calls registerApi() with:
   {
     name: fullName,
     mobile,
     userType: "Customer"
   }
6. If registration succeeds:
   - success toast is shown
   - user is routed to /docListPage?mobile=<mobile>

Validation:
- Full name is required.
- Full name must be at least 3 characters.

API Layer
Endpoint file:
src/apiData/endpoints.tsx

API wrapper file:
src/apiData/api.tsx

Base URL:
process.env.NEXT_PUBLIC_API_URL

APIs:

loginApi(payload)
- Method: POST
- URL: /login
- Payload:
  { mobile }
- Used by LoginForm after OTP verification.
- Expected to return userType and isExistingUser.

registerApi(payload)
- Method: POST
- URL: /register
- Payload:
  { name, mobile, userType }
- Used by registerForm.

getDocumentsNameApi(mobile)
- Method: GET
- URL: /documents/:mobile
- Used by Admin page and Customer document list page.

addDocumentsApi(payload)
- Method: POST
- URL: /documents/add
- Payload:
  { adminMobile, mobile, documents }
- Used by Admin page to assign documents.

removeDocumentApi(mobile, docName, adminMobile)
- Method: POST
- URL: /documents/remove/:adminMobile/:mobile/:docName
- Used by Admin page to remove assigned documents.

Important Known Gaps and Recommendations
1. API auth headers
   api.tsx imports axios directly. To use auth headers from src/axios.tsx,
   import the configured Axios instance instead.

2. Route protection
   Role-based navigation exists, but visible client-side route guards are not
   implemented. Backend must enforce authorization.

3. Role source
   Roles come from backend loginApi response, not Firebase custom claims.

4. Query parameter security
   mobile, adminMobile, userType, and documentType are passed in URL query
   parameters. Backend must validate permissions using Firebase token.

5. Document mappings
   docListPage removes spaces from document names. getForm and getTemplate must
   use matching names such as SampleOfferLetter.

6. PDF preview mapping
   Preview should use getTemplate if more document templates are added.

7. Naming cleanup
   Some names contain typos, such as removeDocumetApiUrl and Documnents.
